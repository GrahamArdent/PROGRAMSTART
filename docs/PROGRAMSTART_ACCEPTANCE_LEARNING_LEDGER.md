## How this ledger is used

The Learning Gate answers:

**REAL PROJECT OBSERVATION → SYSTEMIC / LOCAL / CONFIRMATION / COUNTEREVIDENCE → EXISTING LESSON? → MATURITY DELTA → PROGRAMSTART CHANGE, IF EARNED → REAL RETEST**

Only update this rollup when evidence materially changes a lesson's summary, maturity, strongest evidence, implementation/validation state, or next retest condition.

`No reusable lesson` is a valid result and should usually produce no ledger write.

## Maturity states

- **observe** — plausible reusable signal; more evidence is needed.
- **candidate** — repeated/material evidence supports a bounded change.
- **implemented** — PROGRAMSTART changed; meaningful real retest is still open.
- **validated** — a real retest shows the change altered execution as intended.
- **rejected** — evidence shows the proposed change was unnecessary, harmful, over-broad, or already solved by existing primitives.

Lesson IDs are stable organizational references, not priority or roadmap numbers.

## Recording rules

- Detailed meaningful evidence goes in one observation record, not directly into a growing narrative here.
- Search this ledger before proposing a new lesson ID.
- Strengthen/narrow an existing lesson instead of creating synonyms.
- Confirmation with no maturity impact usually requires no durable write unless it is an explicit acceptance test worth retaining.
- Counterevidence may narrow, demote, or reject a lesson.
- A lesson does not become a feature request merely because it is `candidate`.
- PROGRAMSTART methodology changes require a focused PR and a named real retest condition.
- Product/project completion must not depend on whether the current environment can write to PROGRAMSTART.
- Never store raw secrets or unnecessary private product/user payloads in learning evidence.
