## What happened

The operator asked to recover the earlier idea for an encrypted cross-platform place for passwords/secrets and then clarified the practical objective: reduce repeated manual copy/paste of OAuth material, API keys, deployment credentials, service keys, and other cross-platform secrets while still allowing authorized systems to consume those credentials safely.

The prior architecture was not reconstructed from chat memory alone. PROGRAMSTART's existing acceptance evidence was searched and the August 28 Secrets & Credential Architecture Audit was recovered. That evidence had already established a bounded `$0` pilot recommendation: preserve provider-native runtime secret stores as destination-of-use, use a central broker for cross-provider/operator/local-development/AI-agent gaps, and prefer Infisical Free as the first pilot while retaining alternatives and explicit `PAY_WHEN` triggers.

The operator then asked to turn the idea into durable GitHub authority and explicitly requested PROGRAMSTART-aligned files plus a detailed report on how PROGRAMSTART is performing.

During live GitHub orientation, `GrahamArdent/execution-node-control` was found to exist as an empty private repository. Prior project context and its intended scope showed that repository is the bounded Ubuntu execution/control bridge and is not intended to own central secrets/credential management. PROGRAMSTART's one-project/one-spine and project-authority rules therefore prevented convenience from silently turning that repository into the Secrets & Identity Control Plane's strategic owner.

No dedicated secrets-control-plane repository currently exists in the connected GitHub account, and the available GitHub write surface can create branches/files/PRs inside existing repositories but does not expose repository creation. Accordingly:

1. PROGRAMSTART learning evidence is being written to PROGRAMSTART in a focused branch/PR;
2. project-specific filled authority is not being written into PROGRAMSTART;
3. `execution-node-control` is not being hijacked as the secrets project's owner;
4. the recommended dedicated private repository is `GrahamArdent/secrets-control-plane`;
5. a complete project-authority bootstrap bundle can be prepared now and becomes canonical only when committed to that dedicated project repository;
6. repository creation is an operator/manual gate, not evidence that the project itself is blocked from analysis/design work.

This is the first clean natural retest of the idea-preservation lifecycle added in PR #68: the idea was worth preserving while non-current, later retrieved when the operator returned to it, and promoted deliberately rather than treated as priority merely because it existed in a record.

## Recovered and refreshed decision evidence

### Prior durable evidence

`docs/acceptance/observations/2026-08-28-secrets-cost-gate-retest.md` established:

- provider-native secret stores remain valid destination-of-use boundaries;
- centralization is valuable primarily for cross-provider/operator/local/agent brokering;
- Infisical Free was the strongest initial pilot candidate;
- paid features should be earned by identity isolation, RBAC/audit, rotation, recovery/versioning, or other real requirements;
- volatile pricing/limits are decision evidence, not permanent methodology truth.

### Fresh provider evidence checked 2026-08-30

Current official vendor pages were rechecked because pricing and plan limits are volatile and the operator requested a renewed free-vs-paid comparison.

The refreshed evidence continues to support the prior architecture:

- **Infisical Free:** 5 identities, unlimited projects, 3 environments, 10 Secret Syncs, machine identities, static-secret Agent Proxy, integrations, references/imports and related core functionality.
- **Infisical Pro:** currently advertised at USD $20/identity/month billed annually (displayed $23 non-annual reference), with unlimited identities, access controls, rotation, SAML SSO, 30-day audit retention, secret versioning and point-in-time recovery.
- **Doppler Developer:** free entry path with 10 projects, 4 environments/project, 50 service tokens, 5 config syncs and 3 days of activity logs; Team adds service accounts, RBAC, rotation and longer logs at a per-user cost.
- **Bitwarden Secrets Manager Free:** unlimited secrets, up to 2 users, 3 projects and 3 machine accounts; Teams is currently advertised at USD $6/user/month annually with unlimited projects and up to 20 machine accounts.
- **OpenBao:** remains a powerful open-source/self-hosted alternative, but operating it creates infrastructure, hardening, availability, recovery and audit responsibilities that are not currently justified merely to avoid a hosted subscription.

The resulting recommendation remains vendor-neutral at the architecture level and Infisical-first at the implementation level.

### Friction / limitations observed

The connected GitHub capability cannot create a new repository even though it can create files/branches/PRs in existing repositories. For a genuinely new project whose correct authority must live in a dedicated repo, this creates a small manual bootstrap gate.

This does **not** currently justify a new PROGRAMSTART methodology feature because existing primitives already describe the correct behavior:

- project authority must remain in the owning repository;
- operator/manual gates must identify the exact action and resume point;
- safe work may continue outside the narrow blocked action;
- project completion must not depend on the ability to mutate PROGRAMSTART.

The limitation is therefore primarily an environment/tool capability boundary, not a PROGRAMSTART design failure.

Recommended initial files:

- `TEST_STRATEGY.md` — leak prevention, least privilege, injection/sync behavior, outage/revocation/rotation and acceptance tests
- `RELEASE_READINESS.md` — production/go-live controls and rollback

- `POST_LAUNCH_REVIEW.md` — outcome/cost/operational learning after real use
- `AGENTS.md` — repository-wide AI/automation guardrails, especially secret-safe behavior
- `docs/SECRETS_REQUIREMENTS_CONTRACT.md` — schema each consuming repository can use to declare secret names/consumers/delivery without values
- `docs/PROVIDER_AND_COST_DECISION.md` — current decision-scoped provider evidence and invalidation conditions
- `docs/PROMPT_ALIGNMENT.md` — reusable PROGRAMSTART-aligned continuation prompt and secret-handling instructions

The bundle must not store actual secret values.

## Next real product slice after repository bootstrap

The first implementation slice should be deliberately small:

**Pilot the control plane with one high-value, non-production or safely reversible credential flow before migrating broad secret inventory.**

Candidate shape:

1. create Infisical Free organization/project structure;
2. establish the first human administrator and one bounded machine identity;
3. connect the Ubuntu Execution Node as a consumer without granting unrelated credentials;
4. store/import one low-risk pilot secret or dedicated test credential;
5. prove runtime injection without a plaintext committed `.env`;
6. prove logs/output do not reveal the value;
7. revoke/rotate the pilot credential and verify expected failure/recovery behavior;
8. only then evaluate the first production-relevant project integration.

Repo Watchtower remains a strong later pilot candidate for agent/credential brokering because its GitHub control-plane credentials have meaningful blast radius, but high-risk credentials should not be the very first smoke test.
