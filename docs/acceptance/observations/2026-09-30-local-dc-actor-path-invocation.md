# Observation — Local Desktop Commander bounded proof exposes actor-to-path invocation distinction

Date: 2026-09-30  
Project/system: Paths / Desktop Commander capability investigation  
Status: subordinate PROGRAMSTART learning evidence; not project authority or execution authorization.

## What happened

A bounded proof attempted to determine whether the existing VPS can expose a locally consumable Desktop Commander MCP capability without using hosted Remote MCP transport.

Current Paths evidence records alternate VPS/EN execution and recovery capabilities and requires equivalent-path search before declaring a capability unavailable. Live Remote Desktop Commander discovery showed all three registered devices online, including `vps-743d7c1d`, while the first VPS Remote MCP operation was rejected because the provider-hosted Remote MCP usage allowance was exhausted. The provider instructed not to retry/reconnect that surface.

The current ChatGPT invocation enumerated its available connected tools. It had repository/provider tools and Remote Desktop Commander, but no direct Controller/Compute/SSH/Codex actuator exposed for the recorded alternate VPS execution route. Repository evidence alone could not truthfully prove whether a local Desktop Commander MCP server is presently installed/configured on the VPS.

The proof stopped before installation/configuration, as required.

## Learning Gate classification

**Systemic confirmation plus narrowing evidence for existing PSL-021 and PSL-023; no new lesson ID earned.**

### PSL-021

Confirmed: failure of one provider surface must trigger search for other bounded mechanisms rather than immediate human transport or false capability loss.

Narrowing evidence: discovering an equivalent ecosystem path does not itself mean the current actor/session can invoke it. Alternative-actuation search must include the actor-to-path admission/invocation edge, not only target-side capability existence.

### PSL-023

Confirmed: component/device health and historical/recorded connectivity do not establish current end-to-end readiness.

Strengthening evidence: readiness should distinguish target capability health, path availability, current-actor invocation/admission, and requested-effect authorization/proof. A healthy Remote Device plus a recorded alternate VPS path was insufficient to prove the requested local-MCP observation from this invocation.

## Counterevidence / challenge

This does not prove the Paths registry is wrong, the alternate VPS path is unhealthy, or local Desktop Commander lacks value. The missing element may be only an invocation adapter unavailable to this ChatGPT environment. It does not justify creating a new transport or broadening authority.

## Methodology-change disposition

No immediate PROGRAMSTART methodology change is earned. Existing PSL-021/PSL-023 already contain the governing principles. Preserve this as stronger natural evidence and use the next actor→alternate-path capability proof as a retest.

## Next natural retest

Use an invocation where the existing Controller/Compute/Codex/SSH path is actually exposed/admitted to the actor. With the preferred surface unavailable/bypassed, prove the actor can select and invoke the alternate route for a bounded observation without human transport, authority expansion, or new transport construction.
